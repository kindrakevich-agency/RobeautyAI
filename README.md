# RoBeauty AI Operations — демо-стенд

Демонстраційний стенд операційних AI-агентів для D2C-бренду косметики:
двомовний (UA/PL) консультант поверх реального каталогу та адмінка семи
агентів — від підтвердження замовлень до аналітики людською мовою.

🌐 **Демо:** [robeauty.kindrakevich.com](https://robeauty.kindrakevich.com)

> **Дисклеймер.** Портфоліо-демо для демонстрації підходу. Стенд не
> афілійований з RoBeauty. Дані каталогу зібрані з публічного сайту
> robeauty.me. Замовлення, клієнти та статуси доставки — синтетичні.

## Запуск однією командою

Потрібен лише **Docker**. Усе інше — міграції, скрапер каталогу, індексація,
демо-дані — робиться автоматично при старті.

```bash
cp .env.example .env      # вписати OPENAI_API_KEY
docker compose up -d --build
```

Далі:

| Що | Адреса |
|---|---|
| Публічний чат | http://localhost:5210 |
| Адмінка | http://localhost:5210/admin |
| API | http://localhost:8110/api/health |

**Перший старт займає ~15 хвилин**: контейнер TEI качає модель ембедінгів
(≈2 ГБ), потім скрапер обходить robeauty.me із лімітом 1 запит/секунду.
Наступні старти — секунди: і модель, і сирі дані кешуються в томах.

Що саме робить `api/entrypoint.sh` по кроках:

1. чекає, поки підніметься сервіс ембедінгів;
2. `alembic upgrade head` — створює схему з нуля;
3. якщо немає `data/catalog.json` — запускає скрапер каталогу;
4. завантажує каталог у Postgres;
5. індексує чанки, **якщо індекс порожній** (повторний запуск не переганяє);
6. засіває синтетичні дані (ідемпотентно);
7. стартує API.

## Що таке TEI і навіщо тут bge-m3

**TEI** (Text Embeddings Inference) — сервер від HuggingFace, який тримає
модель ембедінгів у пам'яті й віддає вектори по HTTP. У нашому compose це
окремий контейнер `tei`; застосунок звертається до нього на `/embed`.

**Ембедінг** — це переклад тексту в набір чисел (вектор), у якому близькі за
змістом тексти опиняються поруч. Саме тому пошук знаходить «засіб від
почервоніння», коли на сторінці написано «заспокоює подразнену шкіру»: слова
різні, а вектори близькі.

**bge-m3** обрана не випадково. Вона **мультимовна**: український і польський
тексти лягають в **один векторний простір**. Практичний наслідок — польське
питання знаходить український опис товару без жодного перекладу на льоту. Це
критично, бо каталог українською, а половина покупців у планах — польською.
Альтернатива (окрема модель на мову) вимагала б двох індексів і не давала б
крос-мовного пошуку.

**Self-hosted, і це принципово.** Модель працює на вашому сервері: тексти
каталогу нікуди не надсилаються, вартість не залежить від обсягу індексації,
а версія моделі зафіксована — без прихованого дрейфу якості, коли
постачальник мовчки оновив свій API.

Розмірність вектора — 1024, вона зашита у схему БД (`models.py: EMBED_DIM`).
Зміна моделі означає зміну розмірності й переіндексацію.

### Якщо потрібно без TEI

У `.env` можна перемкнути `EMBEDDINGS_PROVIDER` і вказати сумісний HTTP-ендпоінт
через `EMBEDDINGS_URL` — код звертається до ембедінгів через один модуль
(`app/embeddings_client.py`), тож заміна провайдера не зачіпає решту системи.

## Як влаштований пошук

Гібридний: **вектори** (pgvector, косинус) плюс **повнотекстовий пошук**
(PostgreSQL FTS з `unaccent` для польської діакритики). Обидва списки
зводяться методом **RRF** — фрагмент отримує `1/(60+позиція)` балів від
кожного, тож той, що потрапив в обидва, обходить лідера будь-якого одного.

Далі три запобіжники, і саме вони відрізняють робочу систему від демо:

- **Grounding.** Відповідь будується тільки з наданих фрагментів. Якщо
  найкращий збіг нижчий за поріг — консультант чесно каже «не знаю» і
  пропонує людину, а питання лягає в таблицю прогалин.
- **Медичні питання** (вагітність, екзема, алергії) — детермінована відмова
  в коді, без участі моделі: тут ціна помилки надто висока.
- **Джерела під кожною відповіддю** — назви й робочі посилання на сторінки,
  з яких зібрано відповідь. Це можна перевірити, а не вірити на слово.

### Мультиканальність і зв'язок акаунтів

Діалоги веб-чату, Instagram, Telegram і Viber лежать **в одній таблиці**, тож
агент аналізу та адмінка працюють з ними однаково — коли ШІ спілкується
всюди, діалоги теж збираються звідусіль. Реальні конектори підключаються без
зміни схеми: змінюється лише джерело повідомлень.

`customer_identities` зв'язує акаунти одного клієнта між каналами: людина, що
писала в Instagram і замовляла на сайті — один профіль, а не два. Зв'язок
проставляється вручну оператором або автоматично за збігом телефона, і
зберігає ознаку впевненості.

## Вимірювання якості

Обіцянки «точних відповідей» нічого не варті без цифр, тому в стенді є eval:

```bash
docker compose exec api python -m app.eval.run --save
```

20 еталонних питань (12 uk + 8 pl), метрики retrieval і **сліпий суддя**,
який не знає, звідки взялася відповідь, — оцінює лише обґрунтованість,
корисність і мову. Окремо перевіряються поведінкові кейси: медичне питання
**мусить** відмовити, питання поза базою — чесно сказати «не знаю».

Прогалини знань замикають цикл: питання без відповіді потрапляє в адмінку,
оператор дописує відповідь, вона одразу стає частиною бази — і питання
закрите.

## Корисні команди

```bash
docker compose exec api python -m app.scraper.run     # оновити каталог
docker compose exec api python -m app.indexer          # переіндексувати
docker compose exec api python -m app.translate        # доперекласти PL
docker compose exec api python -m app.eval.run --save  # прогін якості
docker compose logs -f api                             # логи
```
